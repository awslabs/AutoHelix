# AutoHelix configuration

These fields are supported by the version shipping this skill. Check the
installed CLI and the template generated by `autohelix init` if versions differ.
All paths and commands below are examples; adapt them to implemented commands
in the target project. Schema validation does not execute those commands or
establish their runtime/cost, imports, emitted values, or generated artifacts.

```yaml
goal: |
  Reduce runtime in src/solver.py while preserving the existing behavior.

constraints:
  - pytest tests/

scope:
  editable:
    - src/solver.py

metrics:
  - command: python benchmark.py
    values:
      runtime_ms: lower
    capture:
      - results/report.json

# Optional, if a stable measurement and regression tolerance are agreed:
# acceptance:
#   metric_gates:
#     - metric: runtime_ms
#       max_regression_pct: 5  # Illustrative tolerance, not a recommended default.

budget:
  iterations: 3
```

## Goal, constraints, and scope

- `goal` is the improvement requested of each agent iteration.
- `constraints` contains commands that must exit 0. Entries can be strings or
  mappings with `command` and `timeout` (seconds). The default command timeout is
  1,800 seconds. Make it appropriate for the actual evaluator; a timeout bounds
  execution but does not show that setup verification will be cheap.
- `scope.editable` allows paths/patterns; everything else is reverted before
  validation. Alternatively, `scope.frozen` prevents changes to specified
  paths/patterns. Choose one; do not combine them. Without either, code changes
  are unrestricted by scope.
- Prefer relative paths. Copies and scope isolate repository changes, not
  host access: processes can still write to external files and use credentials
  available to the agent.
- Absolute agent/Python executable paths can select an environment. Source,
  evaluation inputs, and normal capture outputs should resolve in the copy;
  an absolute path to the original checkout can accidentally evaluate old code.

## Observations and acceptance

`metrics` and `observables` are aliases for the same command collection. Choose
one key. Each entry takes:

- `command`: the evaluation or evidence-gathering command.
- `values`: optional mapping of metric names to `higher` or `lower`.
- `capture`: optional list of files to preserve from the checks copy.
- `capture_stdout`: defaults to `true`.
- `timeout`: seconds; defaults to 1,800.

Emit numbers on standard output as `##autohelix[runtime_ms=12.3]`. Names must
match `values`. A command can capture evidence without any scalar values.
Capture paths identify files, not directory trees or glob patterns.

Without metric gates, passing constraints can accept a change even if a
measured value regresses. `acceptance.metric_gates` entries name a `metric` and
`max_regression_pct` (default 10). A zero-percent gate prevents positive
percentage regression against the recorded best value; it permits equal
values. A missing gated measurement rejects the iteration. Percentage gates
skip comparison when the reference value is zero, so use a constraint for an
absolute bound when that case matters. An observation command failure does not
itself act as a constraint.

Capture preserves evidence. It does not restore or promote external artifacts
when code is rejected or accepted. Static inspection can check the expected
capture locations and output format; confirming produced values and files
requires execution under the entrypoint's verification policy.

## Agent and reviewer

```yaml
agent:
  type: claude
  # command: /path/to/agent-wrapper
  # model: your-preferred-model
  timeout_seconds: 1800

reviewer:
  prompt: |
    Assess the candidate against the goal. Give concrete feedback supported
    by the supplied artifacts. Do not modify files.
  # model: your-preferred-review-model
  timeout_seconds: 300
```

`agent.type` selects `claude` (default), `codex`, or `opencode`. Optional
`command` and `model` select the executable and model. Respect the user's
installed agent and preferences.

The optional single `reviewer` uses the same backend as the main agent.
`model` and `timeout_seconds` override its settings. Reviewer feedback is
advisory: it informs a later iteration and does not itself reject a candidate.
This configuration does not define agent-produced scalar metrics or multiple
named reviewers.

## Stop conditions

`stop` lists commands, in the same forms as `constraints`, that end the run
early. They run after the baseline and after each accepted iteration: exit 0
stops (the last stdout line is the recorded reason), 1 continues, anything else
is an error (fatal on the baseline, a warning later). `$AUTOHELIX_METRICS` is a
JSON file of the metrics just measured, so a target is
`jq -e '.speedup >= 10' "$AUTOHELIX_METRICS"`; `$AUTOHELIX_ITERATION` is the
iteration number. For a qualitative condition use
`autohelix ask "<yes/no question>"` (an agent judgment: exit 0 = yes, 1 = no,
2 = no valid answer; cost counted toward the run). Use one when the user states
when the run is done; keep the command and any criteria files outside
`scope.editable`. Budgets still apply.

## Budgets and run state

Omitting `budget.iterations` defaults to five attempts, including when `budget`
is omitted, empty, or YAML `null`. Optional `cost`, `time`, and `iteration_time`
may be omitted or set to `null`, which parses as `None` and means no configured
cap from that field. Other limits, such as an agent or command timeout, may
still apply. Time values accept seconds or durations such as `30m`.

A preparation-only template can leave those choices open:

```yaml
budget:
  # iterations: 5  # Omitted uses the runtime default five, not unlimited.
  cost: null       # No configured dollar cap; choose only with reliable reporting.
  time: null       # No configured loop-time cap.
  iteration_time: null  # No main-agent-call cap from this field.
```

Proposed values can stay in comments until selected; retain any stated/existing
budgets. `iterations` differs from the optional fields: when setting it, use an
integer, never `null`. Current validation does not catch that null, but the
runtime expects a numeric iteration limit.

`budget.time` measures elapsed time in the iteration loop, including its checks
and reviews; initial preflight and baseline work happen before that timer.
Total time/cost budgets are checked between iterations, so they can
overshoot rather than interrupt an iteration. Prior recorded usage counts on
resume, and both are checked before starting another iteration: an
already-exhausted cost or time budget starts no new attempt.

`iteration_time` limits the main-agent call and provides remaining-time feedback,
not a deadline for the whole evaluation/review cycle. `agent.timeout_seconds`
defaults to no timeout; when both are set, the earlier deadline applies.
Checks have per-command timeouts. A reviewer inherits the effective main-agent
timeout unless `reviewer.timeout_seconds` overrides it.

`budget.cost` compares accumulated optimization-agent and reviewer costs with
the requested dollar limit, including baseline review attempts. History keeps
each actual model call in the `calls` list, including its role, usage and relative log path. Claude Code and
OpenCode can report dollar costs; Codex can provide calculated API-equivalent
estimates. Only rely on this optional budget when usable dollar usage is
recorded for the selected backend/configuration; missing cost is not evidence
of free usage. Report generation, model calls made by external commands, and
the user's supervising/setup agent are separate.
These boundaries make the budget a run-control threshold, not an absolute
all-inclusive financial cap.

Start with `autohelix run --path PROJECT -n 3`: always a new run, of three
iterations. Continue one with `autohelix resume [RUN_ID] --path PROJECT`:
`--until N` runs up to iteration N (a total; repeating it is harmless), `-n 3`
runs three more. Either overrides only `budget.iterations`; cost and time stay
run totals.

`autohelix archive RUN_ID` hides a run and stops a bare `resume` from picking
it, retaining its history and unlanded commits; `autohelix delete RUN_ID`
removes its history (with `--force`, even unlanded commits). Both leave code
unchanged. Resuming, archiving, deleting, and resetting code or external
artifacts are different operations. Explain the intended operation before
changing state.

## Explain the generated configuration

For setup-only requests, display the complete generated YAML in the final
response before explaining it. Include the full goal and every configured
section, not just selected settings. Comments can clarify defaults or open
choices, but are not required. Then give a numbered walkthrough in the file's
section order, connecting each choice to its effect on the experiment.

After showing the complete YAML at the start of this reference, a walkthrough
could be:

1. **Goal:** Ask the agent to reduce runtime while preserving behavior. This
   guides its work; the checks below supply the configured correctness evidence.
   Edit the goal to change the requested improvement or behavioral requirements.
2. **Constraints:** `pytest tests/` must exit successfully for a candidate to be
   accepted. These are the existing correctness checks. Add or change a check
   when a requirement needs different evidence, after agreeing on that evaluator.
3. **Scope:** Only `src/solver.py` may retain changes. Keeping the tests and
   benchmark outside this scope preserves the evaluation. Widen the scope if
   the intended improvement requires other files; it does not restrict host access.
4. **Metrics and acceptance:** The benchmark tracks `runtime_ms`, with lower
   values preferred, and preserves `results/report.json` as evidence. No metric
   gate is active, so passing tests can accept a slower candidate. The commented
   gate illustrates a possible regression tolerance; agree on a tolerance and
   measurement reliability before enabling it.
5. **Budget:** Three attempts are configured. Total-time, per-agent-time, and
   dollar limits are unset. Choose applicable limits before a requested launch;
   dollar limits depend on reliable backend reporting and do not cover all calls.

This example does not override the default Claude backend or configure a
reviewer. Explain the actual backend/model choices and omitted defaults in the
user's configuration, and flag choices still open.

Finish with the actual validation and execution results, including verification
not performed, followed by commands to verify and launch later. Link the config
and any durable explanation as supporting detail.
